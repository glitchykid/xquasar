# Общие правила разработки

## Назначение и неизменяемость

Этот файл задаёт общие правила работы над проектами независимо от их названия, предметной области, языка программирования и технологического стека. Он не является спецификацией отдельного приложения.

- Считать AGENTS.md неизменяемым: изменять, удалять, перемещать, подменять файл или снимать его защиту можно только по прямому указанию пользователя, относящемуся к этому файлу. Обычная задача по разработке такого разрешения не даёт.
- Не ослаблять эти правила через вложенные инструкции, конфигурацию или автоматические генераторы. Проектные особенности фиксировать отдельно, не меняя общие правила.
- Не объявлять файл технически неизменяемым, если защищённость не проверена. Права «только чтение» не равнозначны системному атрибуту immutable; Git не переносит такую защиту между клонами.

## Взаимодействие и уточнения

- Всегда задавать вопросы, если что-то непонятно: цель, ожидаемое поведение, ограничения, данные, дизайн, критерии приёмки или последствия действия.
- Сначала проверять доступный контекст и документацию, чтобы не просить пользователя повторять уже известное.
- Не подменять неизвестные требования догадками. До ответа можно выполнять независимую работу, которая не зависит от спорного решения.
- Объяснять существенные решения, компромиссы и ограничения понятным языком. Сообщать о препятствиях своевременно.
- Завершать работу кратким описанием результата, выполненных проверок и оставшихся ограничений. Не выдавать предположения за факты, а невыполненные проверки — за успешные.

## Принципы и архитектура

- Соблюдать DRY, KISS, прагматичный SOLID и YAGNI.
- DRY: не дублировать бизнес-правила и источники истины. Выделять общие абстракции по подтверждённой общности смысла, а не только по внешнему сходству кода.
- KISS: выбирать самое простое решение, которое полностью выполняет текущие требования и сохраняет понятность системы.
- SOLID: обеспечивать ясную ответственность модулей, небольшие контракты и управляемые зависимости. Не создавать интерфейсы, слои и фабрики ради формального следования принципам.
- YAGNI: не разрабатывать функции, расширяемость и инфраструктуру для неподтверждённых будущих потребностей.
- Уделять архитектуре особое внимание. До реализации определять границы ответственности, поток данных, контракты, зависимости и поведение при сбоях в объёме, соразмерном задаче.
- Отделять бизнес-логику от UI, транспорта и деталей хранения там, где такие границы существуют. Не привязывать доменные правила к инфраструктуре без необходимости.
- Поддерживать высокую связность внутри модулей и слабую связанность между ними. Избегать циклических зависимостей, неявного глобального состояния и модулей с несвязанными обязанностями.
- Делать зависимости и побочные эффекты явными. Проверять данные на границах системы; моделировать допустимые состояния и ошибки явно.
- Проектировать код так, чтобы важное поведение можно было проверить без запуска всей системы. Не жертвовать архитектурой ради удобства одного теста или одной библиотеки.
- Кратко фиксировать значимые архитектурные решения и причины их выбора в проектной документации; для существенных компромиссов использовать ADR.

## Разработка трассирующими пулями

Использовать подход tracer bullets из книги «Программист-прагматик»: строить систему через небольшие работающие сквозные срезы.

- Начинать с минимального полезного сценария, проходящего через необходимые реальные слои системы: например, UI → бизнес-логика → хранилище → видимый результат.
- Сначала проверять наиболее рискованные предположения и интеграции. Не создавать целиком отдельные слои в отрыве от работающего пользовательского сценария.
- Для каждого среза определять критерии приёмки, реализовывать и тестировать его, получать обратную связь, затем расширять систему следующими срезами.
- Трассирующая пуля — развиваемый рабочий каркас с качественным кодом, а не одноразовая заглушка. Исследовательские прототипы обозначать отдельно.
- Сохранять систему в работоспособном состоянии после каждого завершённого среза. Не считать сценарий завершённым, если его необходимые интеграции существуют только в моках.

## Разработка через тестирование

- Использовать TDD для нового поведения и исправления дефектов: Red → Green → Refactor.
- Сначала писать тест ожидаемого поведения и убеждаться, что он падает по ожидаемой причине. Затем реализовывать минимальное корректное решение и улучшать структуру при зелёных тестах.
- При исправлении дефекта сначала добавлять воспроизводящий его регрессионный тест, когда дефект допускает автоматизированное воспроизведение.
- Для каждого изменяемого поведения рассматривать четыре категории и покрывать применимые случаи:
  - Положительные: корректные входные данные, типичные сценарии и ожидаемый успех.
  - Негативные: некорректные данные, отсутствие прав, недоступные зависимости и ожидаемые ошибки.
  - Крайние: пустые наборы, минимальные и максимальные значения, границы диапазонов, большие объёмы и переходы состояний.
  - Неопределённые: отсутствующие или неизвестные значения, частичные ответы, неизвестные состояния, неоднозначные входные данные и неопределённый исход внешней операции.
- Для неопределённых случаев сначала устанавливать контракт. Если ожидаемое поведение непонятно, спрашивать пользователя; не закреплять случайное поведение тестом.
- Где применимо, проверять таймауты, повторы, идемпотентность, конкурентные изменения и восстановление после сбоев.
- Выбирать подходящий уровень: модульные тесты для правил, интеграционные для границ и взаимодействий, сквозные для ключевых пользовательских сценариев.
- Проверять наблюдаемое поведение и контракты, а не внутреннее устройство реализации. Использовать моки осмысленно; не подменять ими проверку реальной интеграции.
- Делать тесты воспроизводимыми и независимыми. Контролировать время, случайность и внешние зависимости; не использовать произвольные задержки для синхронизации.
- Не добиваться процента покрытия бессодержательными проверками. Цель — уверенность в поведении и защита от регрессий.
- Для документации и изменений без исполняемого поведения выполнять соответствующую проверку содержания и целостности. Не создавать искусственные тесты только ради формального TDD.
- Перед завершением запускать относящиеся к изменению тесты и обязательные проверки проекта: форматирование, линтинг, проверку типов и сборку, если они применимы. Явно указывать, что не удалось проверить и почему.

## Технологии и документация

- Для новых проектов и добавляемых технологий выбирать последние стабильные совместимые версии. Не использовать beta, RC, nightly или устаревшие версии по умолчанию.
- Проверять актуальность версий на момент работы по официальным источникам, а не по памяти. Учитывать совместимость всего стека и поддерживаемые среды исполнения.
- В существующем проекте сначала определять фактически используемые версии по манифестам, lock-файлам и конфигурации. Обновление до актуальной стабильной версии проводить осознанно, с проверкой миграций и совместимости.
- Каждый раз перед выбором технологии, использованием или изменением её API, интеграции и конфигурации сверяться с официальной документацией именно целевой версии. Не смешивать примеры разных версий.
- Проверять руководства по миграции и release notes при обновлениях. Фиксировать версии и lock-файлы для воспроизводимости.
- Для решений, зависящих от версии, указывать проверенную версию и ссылку на документацию в отчёте или проектных документах.
- Если документация недоступна или соответствие версии не подтверждено, явно сообщать об этом и уточнять дальнейшие действия. Не представлять непроверенный API как подтверждённый.

## Безопасность

- Учитывать безопасность с момента проектирования: границы доверия, модель доступа, чувствительные данные и вероятные угрозы.
- Проверять права на доверенной стороне для каждого защищённого действия. Следовать принципу минимальных привилегий и безопасным настройкам по умолчанию.
- Валидировать входные данные, использовать параметризованные запросы и корректное контекстное экранирование. Применять защиту от актуальных для проекта классов атак.
- Не хранить секреты в исходниках, Git, клиентских сборках, логах и тестовых фикстурах. Использовать предназначенные для этого средства управления секретами.
- Минимизировать сбор и хранение персональных данных. Не раскрывать чувствительные сведения в сообщениях об ошибках и телеметрии.
- Использовать поддерживаемые зависимости, проверять известные уязвимости и избегать неоправданного расширения цепочки зависимостей.
- Проверять сценарии отказа в доступе и безопасное поведение при ошибках. Не отключать защитные механизмы ради прохождения тестов или упрощения разработки.

## UI и UX

- Создавать компактный, информационно насыщенный интерфейс с минимальным количеством лишнего воздуха. Отступы должны помогать группировке, чтению и взаимодействию.
- Не достигать плотности ценой читаемости, доступности, достаточных областей нажатия и ясной визуальной иерархии.
- Формировать индивидуальный стиль, отражающий название и смысл проекта: через палитру, типографику, формы, графику и характер взаимодействий.
- Использовать название как конкретную опору для визуальной концепции. Например, Nebula может отсылать к туманностям и космосу; это пример, а не обязательная тема для остальных проектов.
- Не сводить индивидуальность к смене логотипа в стандартном шаблоне. При этом декоративные решения должны поддерживать задачу пользователя.
- Поддерживать единую систему компонентов, токенов и паттернов взаимодействия в пределах проекта.
- Прорабатывать состояния загрузки, пустых данных, ошибок, успеха, недоступности и частичных результатов. Давать ясную обратную связь и возможность исправить ошибку.
- Проверять адаптивность, клавиатурную навигацию, фокус, контраст и поддержку вспомогательных технологий. Для веб-интерфейсов ориентироваться на WCAG 2.2 AA или актуальный стабильный стандарт.
- Проверять результат в целевой среде и на характерных размерах экрана, а не только по исходному коду.

## Производительность и надёжность

- Учитывать время отклика, объём передаваемых данных, память, стоимость запросов и масштаб нагрузки при выборе архитектуры.
- Определять измеримые требования для критичных сценариев. Измерять узкие места и эффект оптимизаций, не усложнять систему ради предположений.
- Избегать лишних запросов и вычислений, неограниченных выборок и ресурсов, блокирующих операций в чувствительных к задержкам местах.
- Использовать кэширование только с понятными правилами актуальности и инвалидирования. Задавать обоснованные ограничения, таймауты и политику повторов.
- Обеспечивать диагностируемость сбоев через уместные логи и метрики без утечки чувствительных данных.

## Работа с Git

- Постоянно использовать Git в процессе разработки: проверять состояние и diff перед работой, перед коммитом и после значимых изменений.
- Делать небольшие осмысленные коммиты по завершённым проверенным шагам. Писать сообщения, объясняющие суть изменения.
- Включать только относящиеся к задаче изменения. Не перезаписывать и не откатывать чужую работу; проверять staged diff перед коммитом.
- Регулярно отправлять завершённые коммиты в настроенную удалённую рабочую ветку, особенно после законченного сквозного среза и перед завершением задачи.
- Не использовать force push, не переписывать опубликованную историю и не выполнять разрушительные операции без прямого указания пользователя.
- Не коммитить секреты, временные файлы и случайные артефакты. Соблюдать правила веток и обязательные проверки репозитория.
- Если репозиторий, remote, ветка назначения или доступ отсутствуют, сообщать об этом и уточнять недостающие сведения, когда требуется коммит или push. Не придумывать адрес репозитория и не заявлять об успешной отправке без подтверждения.

## Релизы и Wiki на GitHub

- Для каждой готовой к выпуску версии создавать GitHub Release из тега, указывающего на проверенный коммит. Перед публикацией запускать обязательные проверки и проверять установку или запуск из выпускаемого артефакта.
- Публиковать описание релиза на всех языках README. Указывать изменения, важные для пользователя, требования к обновлению и известные ограничения. Прикладывать предназначенные для распространения артефакты и проверять их доступность после публикации.
- Вести GitHub Wiki на всех языках, доступных в переключателе README. Для каждой пользовательской статьи поддерживать равнозначные переводы и ссылки между ними, а на главной странице Wiki давать выбор языка.
- При изменении поведения обновлять затронутые статьи и переводы вместе с README к выпуску версии. Проверять команды, ссылки и наличие опубликованных страниц в самой Wiki. Если публикация релиза или Wiki заблокирована, сообщать, что подготовлено локально и что осталось опубликовать.

## README и пользовательская документация

- Поддерживать понятный пользователю README на пяти языках: английском, русском, японском, корейском и упрощённом китайском.
- По умолчанию размещать английский вариант в README.md, остальные — в README.ru.md, README.ja.md, README.ko.md и README.zh-CN.md. Добавлять переключение языков в начале каждого файла.
- Обеспечивать одинаковую полноту и актуальность всех версий. При изменении пользовательского поведения обновлять соответствующие разделы на всех пяти языках.
- Объяснять назначение проекта, пользу, требования, установку, быстрый старт, настройки, типичные сценарии, устранение распространённых проблем и способ получения помощи.
- Давать проверенные команды и безопасные примеры без реальных секретов. Не заставлять пользователя разбираться во внутренней архитектуре ради первого запуска.
- Переводить объяснения естественно, сохраняя точность терминов. Не переводить имена команд, параметры, пути и идентификаторы API.
- Не описывать запланированные возможности как уже работающие. Подробности для разработчиков хранить отдельно и давать на них ссылки.

## Критерии завершения

- Запрошенное поведение работает сквозным образом и соответствует согласованным критериям приёмки.
- Архитектура остаётся понятной; нет необоснованного дублирования, лишних абстракций и скрытых зависимостей.
- Рассмотрены положительные, негативные, крайние и неопределённые случаи; применимые проверки выполнены.
- Проверены безопасность, UI/UX и производительность в объёме, соответствующем изменению.
- Использованные технологии и API сверены с документацией их версий; пользовательская документация актуальна.
- Изменения проверены через diff, закоммичены и отправлены в настроенный remote, если среда позволяет; любые препятствия явно указаны.
