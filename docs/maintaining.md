# Maintaining XQuasar

## Architecture

The scanner checks the standard thumbnail and Fontconfig cache locations inside the home directory. It matches the filename and reads the signature from a regular file on the same mount. Thumbnail entries use the PNG signature. Fontconfig entries use the cache magic and the version and byte order from the filename. The scanner does not traverse personal directories. [Thumbnail specification](https://specifications.freedesktop.org/thumbnail/latest/) · [Fontconfig 2.15.0 cache header](https://github.com/fontconfig/fontconfig/blob/2.15.0/src/fcint.h)

The scanner returns candidates and partial errors to the CLI or desktop. Both show a preview before calling the executor. The executor reopens home-relative directories, checks the object's identity, and rechecks Flatpak's inventory before moving profiles intact to private recovery storage on the same filesystem. An incomplete inventory skips profile moves. Each successful action stands on its own if another item fails.

Application cache discovery probes known directory layouts under the four XDG roots and checks Chromium Simple Cache names and headers. For local Python packages it matches the running interpreter's bytecode tag and magic, and requires a regular sibling source file both at preview and cleanup. After unlinking browser or Python cache entries it tries `rmdir` on the same opened directory so unrelated contents survive. Desktop launchers require matching filename, `X-Flatpak` and `Exec` in the main desktop entry plus the same inventory checks as profiles. [XDG Base Directory 0.8](https://specifications.freedesktop.org/basedir/latest/) · [Chromium Simple Cache header](https://chromium.googlesource.com/chromium/src/+/HEAD/net/disk_cache/simple/simple_entry_format.h) · [PEP 3147](https://peps.python.org/pep-3147/) · [Flatpak 1.14.6 desktop export](https://github.com/flatpak/flatpak/blob/1.14.6/common/flatpak-dir.c)

The catalog walks only the explicit cache layouts in each rule, reusing directory listings across checks. A Firefox HTTP hit requires a bounded plaintext v4 metadata record and a key whose SHA-1 matches the cache filename. The scanner reads only the required parts and keeps the key out of the plan and logs. The startup signatures and HTTP rule were checked against Firefox 160.0.1 on Mint. [Firefox cache architecture](https://firefox-source-docs.mozilla.org/networking/cache2/doc.html) · [Mozilla cache metadata](https://github.com/mozilla-firefox/firefox/blob/main/netwerk/cache2/CacheFileMetadata.cpp) · [pip cache](https://pip.pypa.io/en/stable/topics/caching/) · [Cargo cache](https://doc.rust-lang.org/cargo/guide/cargo-home.html) · [NuGet cache](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders)

The GTK 3 window uses an application stylesheet, a Cairo quasar illustration and accessible GTK controls. The summary counts cache bytes only. Detected categories appear first, and a toggle exposes all supported rules. The optional path list shows up to 200 entries. Scanning and cleaning run on a worker thread, and GTK widget updates run on the main loop. The desktop entry launches the packaged system-Python command with `--gui`. Linux Mint 22.3 provides GTK 3.24.41 and PyGObject 3.48.2. [GTK 3 stylesheets](https://docs.gtk.org/gtk3/class.CssProvider.html) · [GTK 3 Expander](https://docs.gtk.org/gtk3/class.Expander.html) · [PyGObject threading](https://pygobject.gnome.org/guide/threading.html) · [Desktop Entry specification](https://specifications.freedesktop.org/desktop-entry/latest/)

Use Docker for development. The image runs tests as an ordinary user with private temporary homes and the real Flatpak CLI. To iterate after building the image, run `docker run --rm --network=none -v "$PWD:/workspace:ro" xquasar-dev` from the source checkout.

The image targets Python 3.15.2. The CLI also supports Python 3.12+. Filesystem operations use the standard library. [Python 3.15 os](https://docs.python.org/3.15/library/os.html) · [Python 3.12 os](https://docs.python.org/3.12/library/os.html) · [Dockerfile reference](https://docs.docker.com/reference/dockerfile/) · [Flatpak list](https://docs.flatpak.org/en/latest/flatpak-command-reference.html#flatpak-list) · [Thumbnail specification](https://specifications.freedesktop.org/thumbnail/latest/)

To build the installer from the checkout, run `sh packaging/build-deb.sh 0.5.0 /tmp/xquasar.deb`. The Docker suite installs the package, checks its menu launcher on a virtual X display, and exercises the window against temporary homes using Debian's system Python and GTK bindings. [dpkg-deb](https://manpages.debian.org/trixie/dpkg/dpkg-deb.1.en.html)

## GitHub Wiki

Edit the Markdown sources in `docs/wiki/` together. To initialize GitHub Wiki, save an initial Home page in the repository's Wiki tab. The Publish Wiki workflow copies the guides and Home page into the separate Wiki repository, converting links to Wiki page URLs. It runs when a Wiki page is created or guide sources change on main. Maintainers can also run it from the Actions tab. Edit the managed pages in the source repository so changes survive the next publication.

Verify the five language links from the published Home page. [Editing GitHub Wikis](https://docs.github.com/en/communities/documenting-your-project-with-wikis/adding-or-editing-wiki-pages)

## GitHub Releases

For a release, commit user-facing notes for every README language in `docs/releases/vX.Y.Z.md`. Describe changes, migration requirements and limitations. Tag the verified commit with the matching `vX.Y.Z` and push the tag. The workflow runs the Docker suite, smoke-tests the source archive, installs the versioned Debian package, and verifies the desktop launcher before publishing both assets. Keep the asset name `xquasar.deb` across versions. Add direct download links to the READMEs once GitHub serves the published package. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)
